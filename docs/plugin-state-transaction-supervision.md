## 必须先解决的竞争

现有插件状态锁由调用父进程持有。直接把finish_transaction移到子进程会引入问题：父进程异常结束后，其状态锁立即释放；旧清理worker退出前，新调用可能开始恢复同一事务。父进程生存期管道、Linux父死信号和Windows Job能促使worker退出，但不能替代跨进程互斥，也不能假定磁盘系统调用即时结束。

在移动任何恢复/清理变更前，引入按规范状态目标绑定的第二个OS事务变更锁。记录、旧目录改名、候选发布、恢复旧状态、写结果和删除证据都必须使用同一锁身份。锁文件常驻、不按空闲删除，避免持有旧fd的进程与新锁文件各自获得锁。拒绝链接、特殊文件、硬链接及祖先路径替换；锁文件不承载授权信息。

当前实现：`core.plugin_state.transaction_guard`复用ResourceLock，平台数据根下的`plugin-runtimes/state-transactions`保存锁，键为规范目标路径（Windows normcase）的SHA256。锁不写进插件持久化payload目录。发布和恢复入口取得同一事务锁，恢复在无记录时也验证锁可用；忙时在任何记录创建或改名前拒绝。既有低层事务函数由调用方持锁，避免在同一事务内重复取得非重入OS锁。

公共ResourceLock新增加锁后路径/已打开文件身份核对及单链接、普通文件检查，检测获取期间锁文件被替换。它也属于SDK代码库存，SDK代码摘要已变为`5055234979aa7a66ae84b7a9589ff5ee5f4a97115a30e3748f02d824b66bce6c`；旧SDK镜像证据不证明此版本通过。不能声称防御已控制宿主账户的攻击者持续替换锁文件。

首轮原生RPC发现把锁放在状态目录旁会使拒绝调用也新增状态清单条目；已改为上述平台元数据位置，保留原验收断言，失败输出保留。临时r1路径不作为正式布局，也不按名称清理其遗留文件。锁元数据随目标数增长，平台总量与安全退役策略仍开放，不能直接删除仍可能被进程持有的锁文件。

插件状态锁仍覆盖整个invoke的读取、容器执行和提交；事务变更锁只保护实际状态事务变更。恢复worker自己取得事务锁，父进程不能持同一锁等待它。旧worker未退出时，新调用的恢复/发布只能明确报告busy或在同一剩余期限内等待，不能跳过锁继续执行。无记录时的恢复入口也要确认没有遗留writer持锁，不能只靠记录文件是否存在判断worker已退出。

## 验收矩阵

- 独立进程在真实恢复扫描、删除及fsync调用中阻塞：超时/取消后worker退出；无法确认退出时保留证据，新调用不能同时变更。
- 强制结束父进程，在worker退出窗口启动第二调用，验证事务锁阻止并发修改；worker结束后可重复恢复，旧或新状态保持完整。
- 两个同目标进程竞争和不同目标并行；锁文件替换/链接/硬链接、旧记录及损坏/截断结果拒绝，不按名字删除未知目录。
- 提交前失败、旧状态已改名、候选已发布、结果落盘前后、部分清理、记录最后删除的每个阶段保持现有重启测试语义。
- Windows/Linux/macOS原生验证。命令取消、进程强制退出、真实磁盘满/权限失败和断电是不同门槛，不能互相替代。

本设计不改变当前归档预算、SDK接口、插件CLI独立目录或生产信任根。未完成的物理/全平台配额、未知暂存归属、损坏记录修复与父目录/数据持久性继续列入总计划。

## 后续发布worker的锁与授权约束

发布worker应接收宿主绑定的状态目标、候选目录及身份、plugin/caller、授权身份/服务边/私网要求、配置和信任库路径、请求ID与同一绝对期限。身份和边是需要重新满足的要求，不是缓存的已批准许可；请求大小、形状及身份使用现有授权请求边界验证。

worker自己按配置→信任→状态事务顺序持锁，在锁内使用现有有界配置/信任解析和`_read_live_authorizations`重新核验，然后建立记录及改名。父进程不得持这些锁等待worker；既有daemon worker内不能再启动ContentInspector子进程，不能通过放宽子进程所有权来绕过这一约束。发布worker内的直接有界读取受整个worker的期限与父生存期约束。

需绑定worker实际采用的配置/信任路径与其锁作用域。父进程不能仅把线程局部“通过”状态传过去，也不能为了测试方便在正式路径跳过授权。准备与回收仍独立，授权锁不覆盖归档解码/提取/权限准备及后续大树清理。

响应要绑定请求、目标、候选及已提交阶段；无效响应、丢失响应、超时或父死都可能发生在改名之后，必须报告结果未确认并保留日志，由下一次持锁恢复判断，不能宣称未提交或凭父进程异常主动删除候选。只有确认worker退出后才允许下一步；旧worker仍持事务锁时新调用明确busy。

下一批验证必须把fsync和两次rename阻塞/故障注入实际worker，覆盖准备后撤权、服务边/私网撤销、持锁发布与授权变更竞争、结果丢失、父死及跨进程恢复。现有父进程monkeypatch不能继续充当worker执行点证据。目录fsync、真实磁盘满、权限失败及断电仍是独立门槛。

## 锁监督方案约束：三系统句柄移交实验

本次只做隔离临时文件实验，未改变生产锁。探针使用spawn辅助进程、真实OS锁、DupFd或Windows DupHandle，另起独立进程竞争；每种模式核对辅助进程存活、退出但主进程仍持句柄、主进程关闭句柄三个阶段，子进程有期限和finally回收。Windows Python3.12.10、Debian Python3.11.2、ghost-macos Python3.12.2均完成三种模式。

| 锁的取得和释放方式 | Windows辅助进程退出后 | Linux/macOS辅助进程退出后 |
|---|---|---|
| 辅助进程加锁，复制句柄给主进程，仅关闭辅助句柄 | 竞争者可取得锁：不满足互斥 | 竞争者仍被拒绝 |
| 辅助进程加锁并移交，退出前显式解锁 | 竞争者可取得锁 | 竞争者可取得锁 |
| 辅助进程打开文件并移交，主进程加锁，辅助进程退出 | 竞争者仍被拒绝 | 竞争者仍被拒绝 |

三种模式下主进程最后关闭句柄后，竞争者均可取得锁。结论：不能直接把现有ResourceLock上下文搬进worker后返回句柄；其显式解锁会破坏移交，而且Windows不能依赖子进程取得的字节锁在退出后存续。实验源码及逐端结果在F盘cache/probe-lock-transfer-20261015-r1.py、lock-transfer-{windows,linux,macos}-20261015-r1.json，摘要及限制在lock-transfer-evidence-20261015-r1.json。

下一实现的评审条件：

1. 主进程持有真实OS互斥至业务、状态提交及资源清理结束。打开、目录准备及路径身份复核可以由受监督worker执行，但复制句柄须绑定本次请求、父PID和同一dev/inode，避免误接句柄或泄漏。
2. 若主进程取得非阻塞锁，worker必须在其持锁期间完成打开对象与当前路径身份复核，之后才允许执行。未确认、超时、取消或父死只回收本次句柄，不得删除永久锁文件；移交前后强杀、ACK丢失、路径替换、旧进程互斥均须验收。
3. 主进程直接执行非阻塞锁调用仍可能受故障网络文件系统影响。此方案不能宣称任意文件系统上的严格总期限。若支持范围要求硬期限，需由受监督进程拥有完整执行事务，并在其丢失时确保容器停止、状态不发布；单纯轮询辅助进程存活不能提供此保证。
4. 先明确本地文件系统支持边界及上述失败语义，再选择分阶段移交或完整事务进程。ResourceLease包含Docker控制和回收，不应只把JSON读取搬走就宣布整个生命周期已受监督。当前仍保持原生产路径，不为通过小测试牺牲互斥。

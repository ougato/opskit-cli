# 插件沙箱工作目录监督

本文描述当前实现和验收边界。分批实现、失败与修复原文保存在[历史记录](plugin-workspace-history.md)，不将历史快照的通过结论套用于后续代码。

## 目录与职责

平台只在 `data_dir/plugin-runtimes/workspaces` 分配宿主工作目录，不再使用 OS 临时父目录。切换 `TEMP/TMPDIR` 不会增加同一平台的额度。第三方源码仍独立维护；平台向容器提供有界的插件和状态快照，不让插件写平台源码、其他插件或宿主依赖目录。

`core/plugin_workspace.py` 负责受监督分配、请求写入和身份绑定清理；`core/plugin_workspace_budget.py` 负责只读逻辑预算。预算常量也供清理使用，避免分配与回收边界漂移。

## 准入预算

| 项目 | 当前默认值与行为 |
|---|---|
| 目录总数 | 最多 8 个；未知名称的直接目录同样占位 |
| 逻辑字节 | 1.5 GiB；每个目录按 `max(实际字节,192 MiB)` 计账，新增前再预留 192 MiB |
| 条目 | 131104；每个目录按 `max(实际条目含根,16388)` 计账，新增前再预留 16388 |
| 未知普通文件 | 按真实逻辑大小与条目计账，不忽略无前缀文件 |
| 遍历边界 | 深度 66、父目录直接条目 16384；总遍历条目也受预算限制 |
| 异常内容 | 链接、reparse、多链接、特殊文件、权限错误、身份或时间变化均拒绝新增 |

分配 worker 在共享 `platform_state_guard` 内完成规范路径和祖先检查、目录初始化、预算重算与独占创建。已创建目录立即占用完整增长预留，请求写入和快照复制期间也不会失去预留。扫描不读取文件内容，时间 O(entries)、遍历栈 O(depth)，均有硬上限。

这属于同一平台数据根的逻辑准入预算，不是物理块配额或剩余空间预留；不同 `data_dir` 不共享额度。容器镜像、构建缓存、历史 OS 临时目录不在此范围。持久 `plugin-data` 另有独立 1 GiB 逻辑预算，见[状态额度说明](plugin-state-staging-quota.md)。

## 生命周期与安全边界

分配、请求文件写入和清理均在受监督 worker 内进行，分配使用调用剩余期限；清理有独立期限。请求受 JSON 与 UTF-8 字节上限约束，独占写入后核对文件身份和大小；POSIX 下允许容器非特权 UID 只读请求。

父进程只接受绑定请求 ID、绝对路径和目录身份的严格响应。清理必须匹配租约中的父目录及工作目录 dev/inode，完整有界检查后才删除；清理上限仍为 16387 个子条目、8193 个普通文件、192 MiB、深度 66。额度耗尽不阻止已有有效租约的合法清理。

业务失败或取消保持主异常；清理不确定时保留证据并附注。正常业务若清理不确定则报错。分配后响应丢失、父进程死亡、满盘写入失败可能留下没有可用租约的目录；其内容和预留继续计账，不按名称或年龄自动删除。有完整旧租约的历史临时路径仍可按身份清理，未知历史目录不自动迁移或回收。

资源租约是受管工作目录清理的唯一所有者。单有 Python 上下文退出顺序不够：Docker 删除失败时，资源日志虽保留，容器仍可能挂载目录。清理失败保留目录及预算占位；已有主异常保留，不能提交插件状态。当前调用顺序为网络作用域→容器资源租约→目录分配；退出时目录作用域将清理交回外层资源租约，不再额外启动清理 worker，也不再使用两层回调或完成事件传递删除许可。

### 有效资源日志后的跨进程恢复

业务容器在目录分配前先持有 token 的真实 OS 租约并写入 schema1 资源意图。分配worker在共享预算锁内完成准入后，先将同一记录升级到schema3，记录拟创建目录名和父目录身份；意图文件与目录同步并复核确认成功后，才调用mkdir。目录身份确认后、请求文件写入和响应发送之前，再升级到schema2，在原token、backend、daemon、kind、name上增加workspace目录名、父目录及目录dev/inode，移除workspace_intent。两次升级共用同一索引锁、原子替换及写后复核路径，绑定只能匹配原意图的名称与父目录身份。没有接受任意绝对路径；工作目录始终从当前平台数据根和严格UUID名称解析。schema1继续用于旧容器和网络资源，不根据旧名字推导目录归属。

schema3只是已确认的分配尝试，不包含工作目录inode，也不授予删除目录的权限。意图写入失败或确认丢失不得继续mkdir。原580快照一律保留schema3；2026-10-16候选修复仅在调用方仍持token真实租约、确认Docker清理后，由受监督worker按platform budget→resource index顺序持锁，验证父目录身份、日志版本/内容及两次严格目录缺失检查，再退役该日志。分配worker在同一budget锁内写意图并mkdir，index锁排除迟到绑定；存在任何对象、权限错误、锁竞争或身份不确定则继续pending。直接remove_record仍禁止退役schema3，不将一次“当前不存在”观察当作静止证明。该候选跨平台与实际安装验收见最新台账，不代表未知目录恢复完成。活动租约仍跳过，旧schema1父进程允许不可变字段不变的schema1→schema3或schema1→schema2升级；同一租约不重复分配。旧版本遇到未知schema应拒绝处理，不自动降级日志。

`plugin reconcile` 复用现有资源 token 锁：活动租约跳过；非活动租约先匹配 backend/daemon，再移除精确标签/名称的容器 ID，复查不存在并再次核对 daemon，然后用记录身份执行受监督目录清理，最后删除资源日志。目录已不存在时允许幂等重试；父目录/目标替换、权限错误、有界清理失败均保留日志，供后续检查或重试。目录清理后但日志删除前崩溃可重试；不会先删日志再丢失目录归属。

关闭租约时通过受监督 reader 重新读取磁盘记录，只接受不可变资源身份不变的 schema1→schema2 升级；即使分配响应丢失或升级确认丢失，父进程仍持旧 schema1，也能恢复已绑定目录。同一租约只允许请求分配一次，不重试覆盖原绑定。请求写入失败、响应前超时/取消已有恢复路径。

mkdir成功到身份日志成功写入之间仍没有目录身份，因而自动回收窗口尚未关闭；新schema3使这类失败保留可见待处理记录，不再静默退役原日志并返回四项零。历史无意图目录、schema3的显式人工核验/修复、部分/损坏日志和旧schema1都不授权删除未知目录。Docker控制请求的完整部署故障矩阵也仍开放。

### 目录同步与确认

POSIX 下，资源日志创建/升级在文件 fsync 和原子替换后，再用经过身份核对的目录句柄 fsync 日志父目录，随后复核日志版本和内容。即使替换后的字节完全一样，sync 期间 inode/version 改变也不得确认。工作目录绑定前同步其父目录，目录清理后也同步父目录并复核目标没有重现；资源日志删除在 unlink 后同步父目录并检查记录未重现。全部生产调用位于原受监督 worker 内，不增加进程或将文件系统 I/O 移回主进程。

目录句柄在错误路径也关闭；权限、EIO、不支持的 POSIX 目录 fsync 均拒绝确认，不降级为成功。同步失败或超时可能发生在目录/日志已删除之后，结果仍是未确认，不能把异常解释成没有修改；目录清理确认失败会保留其资源日志供幂等恢复。Windows 保留路径/身份及版本复核，但不调用 POSIX 目录 fsync，也不声明等同的断电屏障。

这些屏障未覆盖所有新建祖先目录的同步、设备/控制器对 flush 的承诺或实际断电重启验收。原生调用在故障网络文件系统上也没有硬期限保证。进程崩溃及注入的同步错误不能替代上述场景。

并发清理或快照写入可能使预算扫描观察到变化，此时新分配拒绝；不通过忽略变化或延长期限换取表面成功。未对宿主账户失陷作隔离保证，也未宣称本改造提速。

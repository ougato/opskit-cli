# OpsKit 框架规划与清理清单

本文把源码审查中发现的清理候选和未来框架能力放在一起，供维护者安排后续工作。**这是一份计划，不表示候选接口已经存在，也不授权直接删除代码或用户数据。** 当前行为见[项目架构与功能流程](项目架构与功能流程.md)，插件公开接口见[插件开发指南](plugin-development.md)和[插件规范](plugin-spec.md)。本清单基于文档整理时的历史源码快照；启动专项后续修复以[启动审查进展](启动至首屏审查与待办.md#修复进展)为准。

本次静态核对基于 CLI `bf1b500` 和 Cocos `0a7c569`。下文的全仓搜索只覆盖可见检出内容，不能证明不存在动态调用、外部使用方或其他版本；后续处理前应重新核对。优先级 P1 表示优先减少误导或可见问题，P2 表示需要收集使用场景再处理，P3 表示长期评估，不代表已经排期。

启动入口至首屏的逐文件审查和专项待办以[启动至首屏审查与待办](启动至首屏审查与待办.md)为准。

## 当前边界与目标

当前内置软件、监控、网络和插件管理运行在框架宿主中；外部插件在隔离 worker 中运行，只能依赖 `core.sdk` 公开接口。Cocos 是独立业务插件，不因位于同一工作区而成为框架的一部分。SDK 4、RPC 传输版本和插件服务业务版本相互独立；新增或修改接口必须同步宿主、SDK、worker 转发、文档和测试，破坏性变化需要明确版本与迁移策略。

目标是让开发者用已有交互和受控宿主能力实现业务，框架集中维护通用权限、安全与交互。候选能力先证明至少有可复用的需求，再确定契约；不把某个插件的参数、配置文件或危险操作直接作为公共标准。宿主工具以用户权限执行，可访问项目以外文件；业务确认、宿主授权和服务调用授权各自独立，任何抽象都不能弱化这些边界。

## 框架化候选

| 优先级和候选 | 当前实现与复用场景 | 建议职责及后续契约要点 |
| --- | --- | --- |
| P1：开发流程与菜单模板 | SDK 已有选择、输入、确认、分页、等待、主题和多语言；各插件仍自行组织流程。适用于所有交互插件。 | 先完善示例和约定，沿用现有 SDK；只有重复场景明确后才扩展序列化交互参数。保留面包屑、取消、非交互和中英文语义，授权始终由宿主控制。 |
| P2：工具发现与选择 | `host_find_executable`、`host_file_version`、`host_path_info` 已提供受控底层能力；Cocos 自行选择 Creator、Git 并保存配置。其他编译器或编辑器插件可能复用。 | 评估可配置的发现、校验、选择和已选路径呈现；先定义查询结果、平台范围、取消和授权语义。工具特有的识别、版本和参数规则仍由插件提供；执行仍独立授权。 |
| P2：项目目录登记 | Cocos 自行维护游戏及项目路径；SDK 的 `plugin_data_dir` 提供插件隔离状态，`host_path_info` 提供宿主路径授权。其他项目型插件可能需要同类交互。 | 调研跨插件是否真的需要统一登记或共享；先定义归属、名称冲突、失效路径与删除登记的语义。不能把登记当作目录授权，也不能让插件读取其他插件状态。 |
| P2：Git 流程 | Cocos 使用 `host_find_executable` 和 `host_execute` 实现分支查询与 Git 操作；这不是现成的公共 Git SDK。 | 先区分只读查询和会修改工作区的动作，明确输入、返回、失败和确认。同步、重置或清理可能丢弃用户改动，不能纳入隐式通用步骤；不绕过宿主执行授权。 |
| P2：构建产物历史与清理 | `host_artifacts` 已提供受身份和内容约束的登记、列出、清理等底层能力；Cocos 管理自己的构建结果和业务保留规则。 | 评估通用历史选择、摘要展示与清理交互；底层继续复核凭据、目录身份及保留策略。业务成功码、产物校验和平台规则由插件解释，不能通过目录名称推断可删除。 |
| P2：配置导入导出 | 插件可用隔离状态及受控宿主文件接口；Cocos 有自己的工具和构建配置流程。 | 在多插件需求明确后设计通用版本标记、预览、覆盖确认和可移植字段；不导出秘密、不迁移宿主授权，旧数据迁移需单独校验。 |
| P3：跨插件协作 | `get_service` / `open_service_menu` 已提供声明、指纹和调用边授权下的服务访问。 | 先用独立插件的真实需求验证服务边界，明确业务 API 版本、方法、JSON 数据、错误及撤权后的行为；不将内部 Python 对象和回调跨进程共享。 |

这些能力目前没有新增公共函数名、数据结构或排期。具体设计应先列出至少两个真实调用场景，评估现有 SDK 能否满足，再定义接口、授权范围、版本和迁移测试。若只有 Cocos 需要，优先留在 Cocos。

## 清理与风险台账

### 已确认可清理

目前没有完成外部调用方和运行时路径核验的代码删除项。下表中的旧注释已确认与当前公开 SDK 不符，但具体修改与关联代码处理留待独立变更；本次不修改运行代码。

### 建议修正或重构

| 优先级、位置 | 证据与影响 | 建议和完成条件 |
| --- | --- | --- |
| P1，`software/actions.py` 的 `resolve_bin`、`ensure_installed` 文档字符串 | 源码仍称“插件 SDK 入口”；`core/sdk.py` 的 `__all__` 不含这两个函数，开发指南也说明旧软件 SDK 已删除。易误导开发者绕过隔离边界。 | 修正注释并决定是否保留函数；不能把函数重新导出当成修正文档。核查旧插件、动态引用及测试后，若删除应同步清理专属测试并验证软件功能。 |
| P1，`software/menu.py` 的切换和诊断图标回退 | 有 `⇄`、`🔧` 字符回退，而项目规则要求菜单通过主题 token 获取图标。 | 在主题缺失时仍使用统一 token 回退，检查中英文菜单、各主题和终端宽度；这是界面规范问题，不代表对应功能可删。 |
| P1，`network/menu.py` 的 Ping 结果 | `packets received`、`min/avg/max` 为直接输出的英文，其中前者是面向用户的说明，未经过语言键。 | 审核哪些是协议或行业缩写、哪些需要本地化；同步中英文资源及占位符，验证成功和失败结果。 |
| P2，`network/menu.py` 与 `network/cli.py` 的下载测速 | 菜单经 `speed_test_download`，使用固定 URL、15 秒超时并把部分异常转成 `0.0`；CLI 经 `download_measurement` 使用传入 URL、时长并返回结构化结果。二者最终都调用 `network.http_measure.download`，但包装和错误语义不同。 | 先确定是否需要一致的失败展示、取消和参数；保留菜单和 CLI 各自明确的输入输出契约，覆盖超时、不可达、取消和非交互退出码后再合并包装。不能把 0 速率直接解释为成功。 |
| P2，软件菜单动作与 CLI 交互入口 | `show_install`、`show_uninstall`、`show_upgrade` 在 `software/direct_cli.py` 的无名称 CLI 分支仍有调用；主软件菜单另有操作流程。 | 比较版本选择、权限、取消、错误和结果后评估提取共享逻辑；保留交互入口和有名称 CLI 的脚本化行为，不因代码相似直接删除。 |
| P2，`main.py` 启动边界 | 根命令有轻量初始化分支，但部分具体命令会显式调用 `_boot()`。将所有具名命令描述为绝不启动或写入会误导。 | 逐命令核对副作用并更新调用契约；需要重构时先覆盖帮助、只读命令和交互分支，避免让只读操作意外下载或初始化插件。 |
| P1，Windows 自举测试 | 历史审查中的测试失配已修正；当前验证与未覆盖边界见[启动审查进展](启动至首屏审查与待办.md#修复进展)。 | 继续分别覆盖 Windows 和 POSIX 重入语义，不能把测试失配直接认定为运行时缺陷。 |
| P2，许可证文件 | README 已移除指向不存在的 `LICENSE` 的链接，项目元数据声明 MIT；当前检出没有独立许可证文件。 | 核实项目实际授权文本及权利人信息后补齐；不能仅凭徽章推断缺失文件的完整内容。 |

### 必须保留的恢复与安全边界

- 插件安装、更新、状态提交与恢复依赖事务凭据、身份和摘要；未知或被修改的数据不能按目录名自动删除。现有旧目录和用户数据不会因 SDK 升级自动删除。
- 权限、指纹、期限、资源锁及进程树回收参与执行和提交检查。简化流程时必须保留授权链和撤权复核，不能让 `--yes` 代替信任或宿主能力授权。
- Windows 原生沙盒与用户权限下的宿主工具是不同边界。Linux/macOS 原生插件后端当前未实现；不能以普通宿主进程静默降级。
- 历史验收记录不等于当前版本验收。保留其时间、快照、失败和限制，不将历史通过项写成对当前构建、发布包或真实业务的证明。

## 分阶段实施与验收门槛

1. **先处理误导与可见规范差异**：复核旧 SDK 注释、硬编码图标和文案；修改后检查中英文、主题、菜单与现有 CLI 行为。
2. **核实调用方再清理**：对每个疑似废弃项检查静态及动态引用、外部插件兼容和相关测试；确认无使用方后单独提交清理，保留必要迁移说明。
3. **提炼重复流程**：比较菜单与 CLI 的输入、退出码、取消、授权和错误语义；先补行为测试，再抽取共享逻辑。测速或软件流程如有意保留差异，文档明确说明。
4. **验证公共能力需求**：收集多个插件的真实场景，先使用现有 SDK；需新增时设计接口、权限、失败、非交互和兼容策略，完成宿主与隔离转发、示例、双语文档及测试后才标记为可用。
5. **独立验收**：分别执行源码单测、Windows 真实沙盒、发布包和实际工具/网络业务所需检查；记录未覆盖平台、设备与场景。真实业务和其他操作系统的支持不能从模拟测试推断。

本清单记录静态审查和后续验证条件；本次整理没有执行上述代码清理、迁移或真实环境验收。

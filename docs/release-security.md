自更新默认拒绝没有签名的二进制。SHA256 只能证明内容一致，不能代替发布者认证。Ed25519 信任根需要发布负责人自行管理；本次整改没有生成或上传生产私钥，也没有修改外部 CI 设置。

发布仓库需要配置：

- Actions variable `OPSKIT_RELEASE_PUBLIC_KEY`：32 字节 Ed25519 原始公钥的 Base64。
- Actions secret `OPSKIT_RELEASE_SIGNING_KEY`：对应 Ed25519 PEM 私钥。

CI 构建前用 `scripts/pin_release_key.py` 写入公钥常量；签名阶段通过 `scripts/sign_release.py` 为每个资产生成 `.sig.json`。签名覆盖规范化 JSON 的 `build`、`filename`、`sha256`；发布时上传签名旁车。密钥缺失会使签名步骤失败。私钥不写入项目文件、日志、插件容器或镜像。

运维人员可在本地可信配置中设置 `update.signing_public_key`；只应通过独立可信渠道核对公钥。不能将网络下载中的公钥自动接受为信任根。轮换公钥需要先由旧信任根发布包含新根的受信版本，或由运维人员验证后人工迁移。当前实现仅支持单根，未实现自动轮换和 TUF 元数据过期策略。

下载签名检查和应用前重新检查防止 checksum 旁车及 pending 文件被修改。普通升级 build 必须大于已安装版本；崩溃恢复允许使用本地旧版本备份，这是恢复策略而非网络版本回退。备份目录和配置必须保持私有权限。

本地恢复现使用健康记录中的backup_id，不按目录里最新文件猜测。新备份旁车记录目标路径、升级前后build、旧程序SHA256及替换产物SHA256；缺记录、摘要变化、目标或版本不匹配均拒绝。恢复先在目标旁复制、fsync并校验指定摘要，再原子替换；失败保留程序和恢复记录，已经恢复到同一旧摘要可重试确认。健康记录有普通文件/链接/硬链接/64 KiB检查并原子写入。仍被健康记录引用的备份不因“只保留最近3个”清理而删除。

旧式未记录备份不自动选择，也不自动清除，需运维核对后迁移或手动恢复。备份旁车是私有本地恢复凭据，不是发布者数字签名，无法抵御可同时修改备份、旁车和配置的宿主同账户攻击者。真实跨用户权限、断电事务日志和Windows失联恢复仍待验收。

Windows 延迟替换脚本与宿主文件系统仍信任当前操作系统账户；插件不接触这些路径。宿主同账户的恶意进程可以改配置或二进制，不在插件沙箱的攻击者权限模型内。

Windows延迟应用现采用私有update-jobs/随机ID目录。调度时复制摘要绑定的独立产物，脚本使用安全单引号字面值和.NET精确路径API，不把路径当通配符或命令。helper等待原进程退出，取得与平台一致的暂存区及程序目标字节锁，将产物流式复制到目标旁随机文件，flush/fsync、摘要校验并保留原目标ACL后调用MoveFileEx的REPLACE_EXISTING|WRITE_THROUGH原子提交。没有先rename移走当前程序、Copy-Item直接覆盖或延迟重启时移动共享pending的回退。

Python原子复制/回滚分支另通过有界Windows安全描述符API在提交前复制原目标DACL及继承保护位，失败不替换当前程序；防止临时文件继承目录规则而丢失原有私有访问限制。该辅助函数只复制DACL，不复制owner或SACL，跨账户拥有者及审计权限语义仍须原生部署验收。

实际提交后才写入新版本健康记录；result.json记录applied、failed或applied_recovery_incomplete，后者明确表示程序已替换而恢复记录未完成。update status展示缓存指向的任务白名单结果及实际健康确认。调度成功仍只称scheduled；启动调度不马上重启进入旧程序。启动失败保留签名门槛下的marker重试路径。helper预算120秒包含等待、锁竞争及复制阶段检查；.NET文件系统调用/摘要和进程回收仍无硬实时保证。

## 归档布局与解析前边界

ZIP当前在创建输出目录前分别检查原始与剥离后的完整布局，拒绝规范化重名、文件/目录及父路径冲突、类型与目录标记矛盾；Windows另拒绝大小写路径别名、尾随点/空格、设备名称和非法字符。已有输出文件或路径内链接拒绝，写文件采用xb；竞争文件不覆盖，失败/取消只清理本次已创建的当前文件。多个文件的整体失败回收仍由独占staging承担，共享提取器不删除用户整个目录。归档路径限UTF-8 4096字节和128层，不把元数据阶段的无界读取当成提取额度已覆盖。

标准tarfile.open在extract_tar之前读取扩展PAX头；此前64MiB声明会触发64MiB读取。当前官方安装、Debian内包、缓存校验及插件状态回传均使用core.archive_reader的只读open_tar/open_zip，原始声明在该读取之前拒绝。只有生成构建上下文/插件返回状态的tar写操作继续使用标准写入口；第三方插件在其隔离环境中自行管理归档，不导入宿主服务。

| 解析边界 | 当前限制与行为 |
|---|---|
| tar成员与内容 | 最多100000成员、2GiB声明载荷；每个成员在枚举中检查，不先无限getmembers。调用方可降低额度，不能扩大平台上限 |
| tar扩展元数据 | 单扩展头1MiB、总头数据64MiB；成员名称/链接名称/128字节基础开销及应用PAX字段合计计费64MiB。PAX每个头最多128条原始记录（重复字段也计数），先检查长度数字、范围、关键词/等号/换行及截断再交标准库构造字段；有效字典也最多128键。嵌套8层、头总数最多成员额度的3倍；所有GNU sparse形式及特殊类型拒绝 |
| 压缩tar | 原始/gzip/xz/bzip2；压缩输入和展开跨度各≤2GiB+256MiB，单次读取/解压块≤1MiB；XZ字典≤128MiB，单流/标准零填充，非法尾部拒绝 |
| 压缩缓存与提交 | gzip/xz/bzip2按需解压到私有临时文件，重复读取用磁盘缓存；成功离开上下文前验证剩余压缩尾部，校验失败不进入外层发布；失败/取消关闭并删除本次临时文件 |
| ZIP元数据 | 中央目录≤16MiB，先流读记录检查实际成员数与声明数一致再构造ZipInfo；单盘、≤100000成员、声明载荷≤2GiB，支持正常ZIP64及自解压前缀 |
| ZIP解码策略 | 仅无密码stored/deflated，拒绝BZIP2/LZMA及其他未提供安全解码预算的ZIP方法；明确报错，不回退旧入口。tar的xz/bzip2支持不受该ZIP策略影响 |
| 提取布局 | 显式成员和隐式父目录合计≤200000个不同路径，路径UTF-8字节加每节点128字节计费≤64MiB；ZIP同时计入大小写规范键与原拼写。先限额再创建目录图/输出；共享父目录只计一次，原始与剥离后ZIP布局分别检查 |
| 插件状态 | 沿用32MiB线路字符串、16MiB状态和4096成员；打开tar采用更小的载荷/成员/元数据额度，布局节点上限同步降至8192，字节计费≤16MiB；超额不替换旧状态 |

解析和布局额度是逻辑资源界限，不是进程RSS或硬实时保证。5万重复PAX字段在标准库解析前拒绝，隐式目录预算已覆盖tar、映射tar、ZIP及插件状态；真实Redis7.4.2包正常布局通过，但未执行/编译。仍需最旧Python版本/私有stdlib钩子兼容、特殊文件系统、多平台正式发行包及整次操作期限验收；压缩缓存带来额外临时磁盘占用，额度/磁盘满失败不能绕开事务恢复。来源签名、系统跨用户权限、后续环境/服务写事务和恶意插件完整生命周期仍是独立门槛。

## 原生插件基础验收

原生插件基础验收使用scripts/verify_plugin_native.py，必须提供审核过的--base-image（registry digest）、--lock-file、已安装--cli-entry和不存在的--output目录。脚本只生成并授权自己的合成插件，配置/插件目录/状态和宿主canary均隔离在输出目录；禁止将用户数据目录作为输出。先验证来源格式与原始锁路径（不解析掉链接），再构建。两个监督器调用及一次源码外已安装CLI路由验证参数、状态与基础隔离；原始证据留在输出目录。CLI示例：

```text
python scripts/verify_plugin_native.py --base-image IMAGE@sha256:DIGEST --lock-file REVIEWED.lock --cli-entry INSTALLED_OPSKIT --output NEW_TEST_DIRECTORY
```

占位值须替换为已审核的真实输入。镜像/构建缓存保留供审查，不对Docker执行全局prune；不清理其他用户资源。该检查观察cgroup/tmpfs额度及无网络权限，不能代替内存/PID耗尽、获批网络代理/RPC、执行中撤权、取消、daemon失败恢复、多架构与正式基础镜像漏洞/SBOM验收。

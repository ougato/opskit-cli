# 插件未知归属与损坏日志的维护恢复设计

状态：设计待实现与验收。此文不增加删除权限，不表示现有平台已经支持下面的命令。对应项目健康路线图第3类；当前验收事实仍以 validation-status-20261015.md 为准。

## 问题与现有边界

`core/plugin_workspace.py::inspect_workspaces` 只观察直接子项，名称匹配不证明所有权。`core/plugin_resources.py` 的有效资源日志及真实租约可以支持已绑定资源恢复；schema3只绑定创建意图和父目录，未绑定子目录inode。`core/plugin_state_repair.py` 只修复完整归属头后的损坏尾，不接受损坏头。

因此，mkdir之后、目录身份提交之前的崩溃，以及部分写入/损坏头可能留下无法自动回收的对象。这些对象必须计入容量并保留；不能通过放宽解码、按UUID名字删除、忽略pending或增加重试次数解决。

## 维护边界

第一版只支持单一受保护数据根、单一宿主账户、已核验的本地文件系统。不同数据根、旧版程序、其他账户和外部Docker客户端不会因本平台的一把锁自动静止。多租户及网络文件系统不在首版自动修复支持范围；必须明确拒绝，不能静默降级。

先关闭部署层入口，再取得平台维护准入屏障。所有会分配、启动、提交、恢复或删除插件资源的入口都必须在同一根身份下参与屏障，包括CLI、RPC、服务和恢复任务。不能持整个调用周期的全局独占锁而把正常调用串行化：采用短暂的准入互斥、持久维护意图与每次调用真实租约；准入、租约创建、维护意图检查必须在同一互斥内完成。

维护进程停止新准入，收集并核验已有租约；已有调用退出或由既有监督正常取消后，才进入静止状态。维护意图不是“锁文件存在即安全”：恢复必须持真实OS锁、复核根身份及意图版本。维护进程崩溃后意图继续阻止新调用，显式恢复维护会话，不凭PID或超时自动清除。旧版二进制不检查新屏障，因此部署停止和旧版写权限撤销是必要前提。

Docker不可达、daemon身份改变、任一租约仍活动、未知写入进程或根身份变化，都不得确认静止。镜像/容器名称及标签只是观察，不授权删除未知资源。不得重启共享daemon来获得静止，也不得清理其他应用容器。

现有已观察锁边包括：invoke线程锁→单插件OS锁；目录分配平台状态预算→资源索引；缺失schema3意图退役平台状态预算→资源索引；损坏尾修复平台状态预算→事务guard。资源metadata退役存在索引锁→token锁的非阻塞尝试；持token的正常路径也可能请求索引锁，当前依赖竞争立即失败而不是阻塞。接入维护时不能把这些尝试改成持索引锁等待，否则会制造死锁。此清单是初始调用链审查，配置/信任变更、平台插件安装/卸载、SDK直接内部调用及所有worker分支仍需逐一补齐。

关闭准入后，已经准入的调用可能继续请求下游服务。应允许可信父调用复用其根会话租约并完整退场，同时拒绝新的外部顶层调用；否则维护会使原本可完成的调用中途失败。嵌套服务不额外占顶层槽，但其全部worker/资源必须仍被根会话追踪。不能把线程局部stack本身当成跨进程授权令牌，也不能允许RPC载荷伪造继承关系。

### 已实现的局部运行互斥（2026-10-16）

598候选将`plugin.commands.update/remove`接入与沙箱invoke相同的按插件OS锁，覆盖更新Git操作及信任失效、删除源码及撤权；锁准备有30秒监督预算，竞争立即拒绝，不等待正在执行的插件。更新保留`(False,error)`接口，删除报告ResourceBusy，菜单捕获忙碌并返回。真实独立锁持有进程下，旧实现更新仍进入Git、删除仍删源码的两个反例已保留；相关反例与菜单检查已通过；当前603快照三端全量及安装后CLI验收已独立复核，详见[当前验收台账](validation-status-20261015.md)。

这只排除同数据根、同插件标识的正常平台运行/变更竞争。安装、回滚、构建、配置写入以及不同数据根未因此统一；源码替换身份、更新失败后的信任处置、崩溃恢复和所有worker静止证明继续开放。下表中的完整维护准入仍未实现，不能将这一把插件锁当作部署静止屏障。

### 补充写入入口与锁顺序审查（2026-10-16）

以下结论来自当前工作树调用链审查，尚未实现屏障，不能作为静止证明：

| 写入入口 | 当前行为与接入位置 |
|---|---|
| `plugin/commands.py::install`、`rollback_install`、`update`、`remove` | 创建/删除源码目录、运行git、修改信任记录。准入必须覆盖首次mkdir至失败回滚/信任与缓存处理结束；不能只包CLI。菜单及 `core/plugin_services.py::_guided_install` 同样调用这些API。当前安装失败清理与直接git更新也需要独立事务和竞争审查，维护屏障本身不修复它们。 |
| `plugin/commands.py::set_enabled` → `core/config.py::set_config_value` | 配置锁内重读并保存；应在取得配置锁之前准入。只在插件命令包装会漏掉通用配置编辑API。 |
| `core/config.py::save_config`、`ensure_config` | 保存整个配置和首次初始化也会写盘；`main.py::_boot` 的菜单启动路径调用ensure_config，命名子命令跳过_boot。维护控制入口不得依赖先初始化配置；无数据根的只读检查不得为取得准入创建平台数据。 |
| `core/plugin_trust.py::grant`、`revoke`、`invalidate`、`grant_service`、`revoke_service` | 当前统一由 `_serialized_mutation` 持信任锁。准入必须在信任锁之前；安装/更新和服务授权会复用这些方法，嵌套调用必须继承可信宿主会话，不能重复请求已关闭的顶层准入。 |
| `core/plugin_runtime.py::build` | 不仅创建Docker镜像，还在结尾原子写 `plugin-runtimes/<name>.json`，网络插件可能构建网关。准入覆盖构建到目录发布及失败清理；不能以构建客户端退出推定daemon后台任务已静止。 |
| `core/plugin_integrity.py::write_checksums` | `plugin fingerprint` 默认生成清单，直接覆盖源码中的CHECKSUMS.yaml；只有 `--check` 是验证。受管源码写入应参加相应根会话。任意外部开发目录不能因为使用平台命令就被认作平台数据根所属对象。 |
| `core/plugin_workspace.py::cleanup` 及资源日志底层create/bind/remove | 不只分配会写盘，finally和恢复路径也会变更对象。已准入会话在关闭准入后仍须允许完成这些操作；直接底层调用无可信上下文应拒绝，不能悄悄新建顶层会话。 |

配置路径、插件源码根、平台数据根和Docker daemon是不同资源边界。即使单账户，它们也可能分别由环境变量指定并跨文件系统。首版必须显式绑定每一受管根的实际身份及daemon身份；不能用data_dir的一把锁推导任意plugins_dir已经静止。外部编辑器、直接git和Docker客户端不参与平台协议，必须由部署停止/权限边界排除；无法排除则拒绝应用恢复计划。

锁顺序实现时需区别“新顶层写入”和“已有会话内最终提交”：前者先准入，再按既有配置→信任及状态/预算锁顺序进入；后者只核验仍持有的会话，不在持配置/信任/状态锁时重新获取准入互斥。否则维护线程等待已有租约、已有调用等待准入，会形成循环。维护等待租约时不得持这些下游锁。

撤权也是写入，关闭普通准入后不能无锁绕过屏障。维护会话需要保留明确的管理员撤权路径，绑定同一维护会话及根身份，仍取得配置/信任锁，并继续触发现有运行中授权复查；该路径不能用于授予新权限、启动插件或修改源码。维护期间普通撤权请求应明确报告维护状态和受支持入口，不能返回成功却未持久化。需用实际双进程验证撤权与状态提交、嵌套RPC、维护等待的竞争和有界结束。

| 阶段 | 持久事实与操作 | 成功条件 | 失败后的行为 |
|---|---|---|---|
| 准入关闭 | 受保护维护会话绑定根身份、会话随机ID、格式版本 | 部署入口关闭且新旧写入主体边界已核验 | 保留会话；拒绝修复 |
| 静止核验 | 核对调用租约、资源索引、daemon身份和已知helper | 所有受管写入者已退出；没有不确定归属 | 保留原物与维护意图 |
| 只读盘点 | 受监督worker有界列举元数据，读取有上限的记录 | 无链接/重解析点逃逸，根及直接对象身份前后一致 | 记录不确定项，不递归试探 |
| 生成计划 | 将对象身份、记录字节摘要、已知引用、预计动作写入独占计划文件 | 所有条目明确分类；计划有摘要与版本 | 不进行目标变更 |
| 隔离执行 | 重读计划及对象身份；受保护同文件系统内原子重命名 | 无覆盖、无活动引用；每一步有前置意图及完成记录 | 保留证据；恢复同会话，不重新猜测 |
| 结束维护 | 再核对未完成动作、资源与目录一致性、容量账 | 所有动作有终态；没有不确定项被标作已处理 | 继续关闭准入并给出准确原因 |

计划必须区分“可证明平台归属”“未知归属”“损坏且无法绑定”。只有第一类可以调用现有归属恢复。未知项默认不动；如管理员明确认领隔离，必须绑定实际对象身份和计划摘要，作为单独的人工授权事实。人工认领不把旧目录伪造成有效schema2，也不证明数据可删除。

隔离目录保持私有权限并计入平台容量，不跟随链接、不读取业务内容、不自动上传。跨文件系统rename拒绝，不降级为复制后删除；同文件系统隔离也不释放磁盘空间。初版不提供永久purge，后续如增加必须有独立保留政策、引用检查和逐对象授权。

## 锁与持久化约束

### 宿主worker与父进程退出的交接

当前 `network/worker.py::owned_process` 已有启动门：spawn后先在Windows绑定Job，再发送R，`_owned_target` 收到R才执行目标；Linux同时配置parent-death SIGKILL，其他平台还有真实寿命管道监督。现有保护不能被描述为没有启动屏障，也不能用“父调用租约释放”推导所有helper在同一时刻已经退出。父进程异常退出和helper真正终止之间仍须有明确的维护静止证明。

维护接入应复用这道门，在目标获准执行之前注册并确认helper自己的真实租约，绑定根、根会话和子进程原生身份；创建失败不发送执行许可。父进程先死、子进程在门前/门后退出及迟到文件系统完成都必须进入维护核验。不要把只保存在父进程的描述符、JSON中的父token、PID存在与否或parent-death配置本身当作子租约仍生效的证明。Windows句柄复制和POSIX文件描述符转交的锁所有者/关闭语义必须分别实测；不能假定两个系统完全相同。

`core/plugin_invocation_lock.py::hold` 目前由helper监督打开并把描述符转交调用者，调用者取得真实非阻塞锁后helper确认路径身份并退出，随后由调用者继续持锁。这适合现有调用锁，却不自动提供每个迟到写worker的维护租约。维护实现必须区分“打开锁的helper”与“实际写资源的helper”，防止递归创建无穷个注册worker，也不能把所有正常调用延长成一个全局锁。

新增交接的锁图需要专门证明：不少worker在单插件锁、预算锁或索引锁已经生效后才启动。不能直接在这些位置调用普通顶层准入而反向加锁。可接受的协议必须保证关闭准入、可信父会话确认、helper注册与静止清点之间无空窗，同时不在准入互斥内等待下游锁/worker/RPC。具体协议在实测双进程反例通过前仍属未实现；本节不授予maintenance-bypass参数给插件或JSON载荷。

维护准入锁在既有configuration、trust、平台预算、资源索引及单插件锁之前。不得持索引锁等待活动调用退出；先关闭准入并释放短锁，再等待租约，随后重新核验。现有worker必须能继承有效维护上下文或明确拒绝，不能绕开父进程授权；不引入另一个独立的资源日志权威。

实施前逐一核对现有锁图，特别是平台状态预算与工作目录预算的嵌套方向。任何新增反向边都要先消除；不能仅靠超时遮盖死锁。

计划和动作记录采用独占创建、有限大小、无链接打开、原子替换、写后身份复核。POSIX目录同步需要覆盖会话、计划、隔离父目录及日志发布顺序。Windows应实现并验证所需句柄语义；没有等价屏障时不得声明断电持久性。任何设备flush能力和真实断电结论均需单独证据。

## 实施顺序与验收

### 已实现的安装与回滚保护

当前安装在同文件系统私有wrapper中克隆并校验清单，只在身份冲突检查、空指纹撤销旧授权及不覆盖发布期间持安装OS锁。失败清理只针对本次wrapper并复核目录身份；不删除竞争者占据的目标。发布前信任写入失败则不发布；发布失败可以保留不授予执行权限的空指纹来源记录。公共不覆盖发布能力位于`core/directory_publish.py`，官方归档安装共用该能力。

成功安装返回进程内凭据，绑定父目录、已发布目录和内容摘要；普通发现清单不能授权回滚。回滚先将对象撤入私有wrapper，再核验实际移动对象的身份和内容；替换物不删除，恢复采用不覆盖语义，失败明确保留位置。源码、Git元数据、缓存及空目录变化也受内容凭据约束。实际同名及不同别名的双安装竞争、回滚替换/内容变化、更新和删除与执行竞争，已纳入当前603快照的三端全量和安装后生命周期验收；结果及适用范围统一记录于[验收台账](validation-status-20261015.md)。

原误删反例与独立进程现场保留在`cache/inventory-worker-identity-20261016-r1/`，初次修复证据在`cache/plugin-install-publication-20261016-r1/`。这些历史证据仅对应各自快照，当前状态以603证据为准。

- 源码根、数据根与daemon身份绑定，物理容量、跨账户及外部写入者边界。

### 已实现的候选发布、撤销与中止原语（639–642，2026-10-16）

`core/plugin_install_transaction.py`提供`publish_candidate`、`inspect_publication`与`recover_publication`，为受限获取后的安装编排提供可复核终态。当前菜单、CLI及服务引导安装仍走旧入口，不能将本节当作宿主Git风险已消除。候选与响应在受监督worker中复核；`plugin_fetch_review._review_tree`由内容审查与发布共用，不复制另一套manifest/入口/原始树规则。

| 阶段 | 实际行为与不确定结果 |
|---|---|
| 最终复核 | 原响应绑定、完整原始树、manifest摘要、指纹、内容凭据与CHECKSUMS状态必须与先前review一致；忽略文件、空目录、执行位和额外硬链接变化也不能放行 |
| 序列化 | worker同步取得既有按插件OS锁，再取得既有安装锁，最后取得信任事务锁；不在daemon worker内再spawn锁helper；不同数据根/外部写入者尚未因此统一 |
| 持久意图 | 在插件根的隐藏平台目录`.opskit-install-transactions`独占发布不可变JSON；绑定插件根/数据根的路径与身份、工作区与candidate身份、目标别名、报告commit/归档摘要、清单及内容凭据；每条至多16KiB、最多256事务，为完成记录预留条目 |
| 撤权与发布 | 意图读回后先invalidate旧信任及服务边；持信任锁复核当前内容，再使用已有不覆盖目录发布。跨文件系统移动失败，不降级为复制/覆盖；没有删除竞争目标或自动信任的路径 |
| 完成记录 | 对实际移动目标复核身份/内容，核对意图，调用工作区和目标父目录同步后独占写入完成记录；记录绑定规范化意图SHA256。Windows目录同步仍不提供POSIX fsync或断电承诺 |
| 只读检查 | 复核现有记录、根身份及拓扑，返回prepared/published-unconfirmed/published；不取得会创建文件的锁，不重建缺失锁，不chmod，不推进事务 |
| 显式确认恢复 | 取得相同OS锁后，仅对实际已移动、内容与身份精确匹配的published-unconfirmed重新撤权并补齐完成记录；prepared原样返回，不替用户发布；未知拓扑、损坏/外来记录和内容变化均保留并拒绝 |
| 显式撤销 | 新的空工作区必须与原工作区不同；`.withdrawal.json`绑定原意图与该工作区，撤权后不覆盖移动精确候选，复核后写`.withdrawn.json`；不删除树；通用恢复只确认withdrawn-unconfirmed，不执行withdrawal-prepared的移动 |
| 显式中止 | `abort_publication`只接受完整未变的prepared候选，撤权后写绑定原意图的`.aborted.json`，不移动或删除；通用恢复不会替调用者选择中止。矛盾标记、发布目标或内容变化保留并拒绝 |
| 记录退役 | 撤销或中止的工作区须先单独显式清理，发布目标必须不存在；不可变`.retired.json`包含原意图、撤销信息（中止时为null）及精确记录版本/摘要，每次unlink前复核。主意图已删除也可继续；inspect/recover只返回retiring。未知/新增/变化记录保留，absent只说明当前无记录 |

调用者收到异常或超时时必须保留工作区及事务token，不能放进会无条件删除工作区的失败finally。成功后可以调用既有按身份清理工作区；已发布内容与事务记录独立保留。641/642已提供显式撤销、中止和记录退役的局部协议，但用户拒绝信任、安装失败、更新/删除与这些API的主流程接入仍未完成；记录不会按年龄自动清理，也不提供purge。每条记录仍最多16KiB、最多256个事务，每事务最多6个固定文件；未知文件拒绝，不把未知记录当成空闲容量。

现有POSIX根检查要求所有者私有mode；Windows目录检查拒绝外部写/删除/改所有者权限，JSON文件独立使用私有ACL。外部可写根在取得锁前拒绝；现有ResourceLock仍可能收紧已允许的只读目录ACL，发布/恢复不保证完全不改受管根权限。只读inspect不调用该锁或权限修改。保护范围仍为可信单账户、本地受保护文件系统；不证明敌对祖先替换、跨账户/数据根或网络文件系统安全，也不证明完整维护静止。进程级期限与单点SIGKILL恢复不替代断电或不可中断内核I/O故障验收。

匹配639源码的三端相关矩阵及真实组合、SIGKILL和锁竞争证据统一见[Git获取边界](plugin-git-acquisition-security.md)与当前验收台账；最低Python终态按台账记录，不从其他端通过推断。下一步将完整准入、来源/分支记录、信任确认/撤回及更新切换接入同一编排，再迁移和移除宿主Git入口，不长期保留双轨实现。

### 安装/更新主流程的接入协议（待实现）

以下为主流程实现约束，不能把已有局部API当作这套流程已完成的证明。接入以一条真实可用流程为单位，避免先增加没有调用方的通用框架。

**来源与工具选择。** 平台安装凭据在首次发布前持久绑定规范化来源、分支、原始commit、当前目录身份和完整内容凭据；私有profile内容及路径、代理token不进入来源记录。HTTPS/SSH来源复用既有纯规范化校验，本地来源只记录经校验的绝对源路径及当次commit，不要求日后原目录继续存在才能恢复安装事务。插件仓库里的`.git/config`、manifest和可修改的信任记录都不能替代不可变安装来源。无有效平台安装凭据的手工clone继续允许独立发现/信任/运行，但平台更新不得猜测其归属或自动覆盖开发者修改。

固定工具镜像由平台`prepare-fetch`准备并保存内容寻址选择；每次使用复核实际本地daemon、当前源码/锁摘要与镜像策略。不得把测试机镜像ID写为所有开发者的默认值；缺少有效准备时明确拒绝，并指向准备入口，不回退宿主Git。凭据每次显式提供且绑定精确来源；私网能力只对本次目标放行，不持久自动扩大更新网络权限。

**安装决策。** 获取/准备/审查返回不执行插件的候选提案，菜单及服务引导可据此显示权限和指纹，再记录与该内容绑定的用户决定；不要在发布前直接grant，否则可能误授权同名旧目录。CLI普通安装保持“不自动信任”。发布时重新核对提案、根及内容，撤旧授权后发布；只有明确批准且实际发布对象仍匹配，才允许按既有授权事务授信。拒绝尚未发布的提案直接走明确归属的候选退出；已经产生prepared意图则显式中止，已发布但需撤回则使用撤销协议。失败后的清理依据所处事务状态，不能一个finally无条件删除工作区。

**更新切换。** 在维护准入会话内先获取新候选，长下载不持插件/安装锁；切换阶段按插件→安装→信任锁复核当前来源、旧树和新提案。新事务须同时绑定前任安装事务、原目标、旧完整凭据、两个候选目录身份、备份工作区及新来源/commit，独占记录切换意图后才撤权和移动。旧树不覆盖移动到备份，新树不覆盖移动到原目标；对实际移动对象重新核对后才记录提交。不允许以“先git pull覆盖、再发现降级/校验失败”实现拒绝；版本回退是切换前的显式决策。

| 更新观察拓扑 | 可确认的事实 | 允许动作 |
|---|---|---|
| 旧树仍在目标，新候选仍在工作区 | 切换尚未移动 | 保留prepared，显式继续或中止；通用恢复不替用户发布 |
| 原目标不存在，旧树在精确备份，新候选仍未发布 | 中间移动已发生 | 保留所有对象，依据已绑定的显式继续/恢复旧版决定行动；不按目录名猜测 |
| 新树在目标、旧树在精确备份，缺提交记录 | 两次移动均已发生 | 复核双方内容/身份与意图后确认提交；不授信，不先删除备份 |
| 提交已确认，旧树或新树后来变化 | 不能再推导安全删除/回滚 | 保留变化对象并报告，不把开发者修改当临时垃圾 |
| 目标/备份/工作区或记录互相矛盾 | 归属与完成状态不确定 | 拒绝变更，保留对象；转入有准入静止证明的维护恢复 |

新版本提交后，旧树仅能依据它的精确凭据清理。前任记录退役必须绑定已完成后继事务及当前新树身份；不能直接调用当前要求“目标不存在”的641退役API，也不能为绕过这个检查先删除备份和旧记录。切换中断仍需能确认或显式回滚；任何恢复都不能覆盖后来出现的目标。升级不得继承旧指纹或服务授权，默认要求重新核对信任。状态目录保持独立，不能用源码更新顺便删除状态。

业务服务承接以上规则，CLI只解析与输出，菜单只展示提案和收集决定，服务引导安装复用同一业务服务。替换完成并以同一候选通过源码、安装包和真实服务/取消/崩溃验收后，移除旧clone/pull及仅服务它们的辅助代码；维护准入、全链路I/O及跨根/其他写入入口不得因主流程绿色而省略。

菜单回滚、双安装竞争和内容变化保护已有验收，不能继续作为未实现项反复重做；上述完整事务门槛也不能因局部用例通过而关闭。

1. 绘制所有准入及写入口、根解析和锁顺序清单；使用真实双进程反例证明维护窗口仍可发生新分配的位置。先补屏障及维护会话恢复，不增加删除功能。
2. 接入只读盘点和有界计划，覆盖schema1/2/3、损坏头/尾、未知目录、FIFO、符号链接、Windows junction、超额条目和权限/EIO。只读操作不得创建运行目录或改变对象时间戳。
3. 验证活动调用、启动中worker、迟到绑定、RPC、撤权和恢复任务与关闭准入的竞争；所有潜在写入口必须被覆盖，不能只测CLI包装层。

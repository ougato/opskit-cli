# 插件安装流程

Windows x64 安装菜单只要求输入仓库地址，并在审核页面决定是否信任插件。用户亲自提交的地址允许本次连接其解析出的私网或保留地址，目标仍限定为该仓库的主机和端口；缺少认证或服务器身份无法验证时，按实际问题请求凭据，不跳过 SSH 身份或 HTTPS 证书校验。更新已有来源时私网连接仍须本次确认，命令行需要显式 `--allow-private`。首次使用自动准备采集工具和 SDK 运行环境，不需要填写 Python/Git 目录或运行内部准备命令。

Windows 源码入口 `python .\main.py` 会复用已有的项目 `.venv`，尊重用户明确选择的其他虚拟环境；不修改系统 Python 的依赖。缺少传输依赖时报告环境依赖问题，不再混同网络失败。首次准备包含独立工具快照、内容校验和沙盒自检，随后复用已验证的 catalog。纯 Python 标准库以一个未压缩 ZIP 保存，原生扩展保留普通文件，减少隔离阶段的小文件复制和 ACL 操作。

宿主运行依赖以 `pyproject.toml` 为准，源码安装使用的 `requirements.txt` 必须保持相同的依赖及版本约束，并由回归测试校验。隔离采集所需的 Dulwich 同样属于宿主发行依赖；缺失时在工具准备阶段报告依赖问题，不应误报网络、空间或权限错误。升级源码增加依赖后，需要同步更新项目虚拟环境，不能仅复用旧环境中的已有包。

## 顺序

1. 验证输入、目录别名及已有安装冲突。
2. 校验已准备的采集工具；需要重新准备时，优先发现本机 Python/Git，将必要文件复制到独立目录并在 AppContainer 内自检。Python 快照包含根目录和 DLLs 目录中的扩展模块（包括 `.pyd`），自检实际导入采集与 SDK 所需的标准库，避免只验证能启动就误判可用。只对缺少、不兼容或自检失败的组件下载固定版本输入，验证大小、SHA256 后安全解压。SDK 依赖要求 CPython 3.14 Windows x64，其他 Python 版本不会强行复用。
3. 使用受限 HTTPS/SSH 获取 Git pack，在隔离 Git 中审核与导出已提交内容。
4. 检查插件清单、SDK 版本、名称冲突和内容凭据。
5. 使用平台固定的 SDK wheel 与哈希锁自动准备运行环境；绑定插件指纹、SDK 摘要与全量文件清单，校验后发布。
6. 原子发布插件目录，初始不授信。
7. 菜单展示名称、版本、类型、权限；用户确认信任后才显示安装成功。拒绝或取消时按照本次目录身份和内容凭据回滚，遇到独立写入者则保留并报告。

命令行 `plugin install` 同样自动准备环境，但继续保留显式 `plugin trust` 的授权模式。服务提供方引导安装复用候选获取和运行时准备。宿主在发布前展示候选来源、指纹、权限和服务调用范围，用户只需确认一次。发布后由宿主写入授信和服务授权，随后返回发起调用的菜单流程。

交互安装、服务引导和终端中的 `plugin install` 共用单行状态。首个状态前留一空行，以彩色点阵动画显示当前阶段，完成、失败或取消后清除。认证和网络确认期间暂停动画，阶段切换维持同一行。重定向输出保留最终结果。Git 隔离命令失败只报告固定步骤和数字错误码。

## 更新已安装插件

在菜单中选择「更新插件 → 更新全部」。框架逐个显示插件标题，再检查已记录的仓库和分支。无明确总量的阶段使用彩色点阵，已知总量的下载或候选复制使用实际百分比。更新成功后保留插件信任，按任意键继续下一个。

更新时，框架会先为新版准备运行时，再报告更新结果。可校验的既有运行时会保留原有 Python、依赖和锁，按新版插件指纹及当前 SDK 发布新运行时。已装入新版但仍指向旧运行时的插件，在选中时自动恢复，前提是安装凭据、当前授信和旧运行时文件均能通过校验。

命令行用 `opskit plugin update NAME` 更新单个插件，或用 `opskit --output json plugin update --all` 批量更新。当前安装需要授信时，先用 `opskit plugin show NAME` 核对指纹，再用 `opskit plugin trust NAME --fingerprint SHA256` 完成授信后重试。详细参数和退出码见[插件生命周期](cli-contract.md#插件生命周期)。

## 发布验收

插件维护者修改仓库中的文件后，执行 `opskit plugin fingerprint <插件仓库路径>` 重新生成 `CHECKSUMS.yaml`，并随改动一并提交。从 OpsKit 源码目录运行 `python -m scripts.check_plugin_release <插件仓库路径> --index` 校验暂存树。提交后用同一命令加 `--ref HEAD` 校验将推送的提交。

在标准的 `opskit/cli` 与 `opskit/plugin/<插件>` 布局中，将框架的 `scripts/plugin-pre-push` 安装为插件仓库的 `.git/hooks/pre-push`。每次推送分支或标签前，钩子校验实际发送的提交。失败时重新生成清单并提交修复后再推送。更新端只校验收到的清单。

生命周期变更要从已授信的旧版安装开始，通过「更新全部」获取远端候选，验证授信保留、运行时准备、菜单可进入及再次更新的结果。候选清单不匹配时应报告清单错误，保留当前安装和授信，并继续处理批量更新的其他插件。

## 失败与重试

- 工具准备、仓库传输和运行环境准备分别报告错误，不提前显示“正在克隆”。
- 工作区创建和清理失败单独提示；其他安装异常在数据目录的 `logs/opskit.log` 中记录阶段、异常类别和代码位置，不记录仓库凭据或原始异常内容。
- 临时工作区容量不足时，自动尝试逐个恢复有有效归属记录且未被使用的工作区并重试；活动、归属未知或身份不匹配的目录一律保留。目录锁短暂忙碌时有限重试；无法恢复时提示进入插件维护的临时清理。
- Windows 数据目录允许使用系统短路径名；创建工作区前仍逐级拒绝链接或重解析点，并验证目录身份。
- 准备失败不发布插件；已完成且通过校验的输入和工具可供重试复用。
- 在插件菜单按 Ctrl+C 或 Ctrl+D 正常退出时，框架收回插件状态，通过复核后保存，再结束主菜单。进程被强制终止时保留可核验的清理记录。之后每次调用使用自己的临时工作区，持久配置从插件数据目录读取。未知目录、被替换的目录及无法验证的记录不会强删。
- SSH 握手前断连属于连接错误，不请求用户填写认证文件；服务器密钥不匹配继续拒绝连接。
- 自动环境包含 SDK 基础依赖。插件额外依赖只能来自审核过的离线输入，不运行仓库 requirements/setup.py 或宿主 pip。
- Linux/macOS 后端仍明确拒绝未实现的原生执行；不降级到宿主 Git/Python。

## 固定输入来源

`core/plugin-bootstrap.json` 随源码、wheel 和 Windows 可执行文件一起发行。Python 摘要来自[官方 Sigstore 文件](https://www.python.org/ftp/python/3.14.10/python-3.14.10-embed-amd64.zip.sigstore)，MinGit 摘要来自[Git for Windows 发行校验表](https://github.com/git-for-windows/git/releases/tag/v2.56.0.windows.4)，SDK wheel 摘要与文件 URL 按各固定版本的 PyPI JSON 核验。运行时不查询 GitHub releases API 或选择 latest。

## 本次验证

- 空数据目录：自动准备工具、隔离采集本地 Cocos 仓库、自动生成并校验运行环境，保持未授信。
- Windows 可执行文件：同样验证首次自动准备和安装；只对自建无业务测试插件显式授信并验证沙盒启动及 SDK/依赖导入。
- 自动准备顺序、失败不发布、取消传播、拒绝信任回滚、目录替换保留、校验失败不写缓存、缓存复用、多语言及发行资源包含已加入测试。
- 真实远程来源 `git.icerror.top` 在 SSH 身份校验前断连，尚未验证该服务器的远程安装成功；不将本地仓库成功代替远端验收。

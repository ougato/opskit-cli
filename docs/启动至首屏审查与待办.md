### 待更新与恢复条件分支逐文件补查

`_boot()` 调 `core/updater.py:check_and_apply_pending()`。冻结包先核对索引事务；缓存没有 `apply_job` 时，先导入 `core/update_reconcile.py` 与 `core/update_target_state.py` 检查是否有工作，即使最终没有工作也可能加载它们。需要核对事务时由 `core/update_cli.py` 使用 `network/worker.py` 的受限 worker 调 `core/update_reconcile.py`，随后视状态进入 post-update、旧文件清理、健康检查、marker 和 pending 检查。`core/update_cli.py` 在父进程此前注册命令时已导入；worker 是独立子进程，其导入应另行采集。源码模式跳过索引事务恢复和替换源码，但仍可能清理旧文件、读取健康状态与缓存或移除 pending。Windows 的替换可通过异步 helper，POSIX 替换后可能重启。下列为静态追踪到的条件依赖，执行与否取决于平台和记录，不代表每次启动均加载或已实机验收。

| 文件 | 在此启动条件分支中的职责与处理原则 |
| --- | --- |
| `core/updater.py` | 编排待更新、健康检查、marker、验证及应用；基本文件大小和平台魔数检查不能代替后续签名与摘要验证。固定名称清理存在 A20，缓存读写边界见 A23。 |
| `core/update_cli.py` | 在需要核对事务时启动有期限的恢复 worker 并接收结果；调用失败需保留未知状态，不能假定已恢复。 |
| `network/worker.py` | 管理可回收的后台 worker 及期限；取消或超时时应验证子进程回收，不能把返回前超时当成事务已成功。 |

| `core/update_windows.py` | Windows 更新执行及辅助进程路径，事务和目标受限于实际 helper 状态。 |
| `core/update_job_cache.py` | 更新任务记录及已退休任务的索引处理；未知或活动状态不得按过期目录清理。 |

进一步的条件边界：冻结包存在 marker 时按记录及锁状态加载任务、目标状态和核对模块；候选摘要通过标准库 SHA256 验证，不加载第三方验签依赖。Windows 替换路径才加载 `core/update_windows.py`，调度时再按需加载 `core/update_job_cache.py`；`core/windows_permissions.py` 也只在相应 Windows 原子复制路径导入。恢复 worker 在 Windows 附着进程时才加载 `core/windows_job.py`。因此文件位于本表并不说明每次启动均调用其所有函数。

## 待办：先修正确性，再重构和优化

下列条目保留原始审查时的问题、建议和优先级；实际状态以开头的“修复进展”为准。P1 为优先处理的稳定性、可见行为和安全边界，P2 为明确契约后处理的结构及效率问题。标记“已复现”的实验均使用隔离目录或模拟，不代表真实发布包已经验收。

### P1：稳定性和用户可见行为

**A1｜Windows 控制台回调寿命** — `core/cleanup.py:92-159` 在局部定义 `ctypes.WINFUNCTYPE` 回调并传给 `SetConsoleCtrlHandler`，未发现持久强引用，也未检查注册返回值。隔离模拟中，注册成功后函数返回并执行 GC，弱引用已失效；若操作系统仍持有对应原生函数指针，真实控制台事件可能调用失效地址。真实 Ctrl+C、关闭窗口和崩溃尚未在本次触发。保留回调到明确注销或进程退出，处理注册失败及重复注册，检查线程和重入；用模拟 GC 测试和独立 Windows 控制台子进程分别验证 Ctrl+C、Ctrl+Break、窗口关闭与正常退出，不在生产进程中注入信号。

**A2｜导入提前初始化日志** — `main.py:606` 加载 `plugin/lifecycle_cli.py` 的依赖，`core/plugin_integrity.py` 等模块顶层调用 `get_logger()`；`core/logger.py:85-89` 会使用默认级别初始化。之后 `_boot()` 调 `init(cfg.log.level)`，因 `_initialized` 直接返回，用户的 INFO/DEBUG 设置不配置预期控制台 handler。隔离进程已复现：`import main` 后 logger 已初始化，后续 `init('INFO')` 仍只有文件 handler。重构为导入阶段不抢先配置，或让明确的启动配置安全更新 handler；保留延迟打开日志、脱敏、幂等与无重复 handler，验证 INFO/DEBUG/WARNING、只读命令、导入边界和失败情况。

**A3｜导入时固化多语言面包屑** — `main.py:973` 装配 Oh My Zsh 命令时加载 `software/recipes/ohmyzsh/impl.py:73-75`，`_BREADCRUMB_BASE` 在 i18n 初始化前调用 `t()`。实测中文初始化后该列表仍为 `menu.software` 等键，而实时翻译为“软件管理”等。改为展示时获取当前语言，核查其他顶层 `t()` 的调用；测试首次启动及中英文切换后菜单和命令行标题。是否延迟导入是独立的性能决策，不能只靠调整导入顺序掩盖语言切换问题。

**状态：回滚未修复；已增加部分确认保护。** 现有 Windows 打包程序在未确认版本达到回滚门槛后，仍试图同步替换正在运行的 EXE，真实隔离实验收到 WinError 5；失败后普通命令仍以 0 退出。健康记录、备份和已准备的回滚事务会保留。当前回滚前先持久化失败计数，达到门槛后即使回滚失败也拒绝确认；冻结程序的健康确认还持更新数据锁与目标锁，核对目标摘要和事务状态，未中止的回滚事务拒绝确认；升级事务的健康记录带 job ID 时还核对本数据目录的 schema 2 job 与备份归属。旧 schema 或缺失 job 会拒绝确认并保留记录，可能需要人工或后续恢复协议处理；没有目标事务但健康记录含 job ID 时拒绝确认；无 job 的旧记录仍沿用原确认路径。健康记录带 job ID 时若只剩回滚事务（包括已中止），因缺少原升级归属而拒绝确认。读写或锁异常也保留原健康记录。这不覆盖跨进程决议持久化失败、旧版进程不遵守保护和异步恢复；下列设计不是现有 API。

**设计修正：**下文原先提出仅在未确认阶段持有健康启动租约，这本身不能协调已经进入业务的旧进程，也不能判定短命令正常完成还是异常退出。后续协议必须覆盖所有实例的完整生命周期及更新任务交接，并明确多数据目录事务归属、短命令和旧事务迁移；不能直接按下方租约草案实现。进一步的约束和验收矩阵见[更新健康与进程租约协议草案](更新健康与进程租约协议草案.md)，该草案同样尚未实现。

独立临时目录此前复现三种确认风险。`tests/test_update_rollback_open_risk.py` 现在使用有效备份凭据、真实目标事务及模拟替换失败验证已准备回滚的确认保护，同时覆盖普通升级确认和目标锁争用；没有事务时回滚失败也会保留达到门槛的计数并禁止确认。另一个进程在健康决议写入失败后仍能确认，仍标为严格预期失败。另用复制到临时目录的 Windows 系统命令验证运行中 EXE 的替换限制。严格预期失败不是修复通过。

`tests/test_update_windows_process_handle.py` 在独立 Windows 进程中验证了可继承的仅同步权限进程句柄：宿主存活时等待超时，宿主退出后等待成功。这只是恢复工具所需原语，不是已接入的回滚实现。同文件另有严格预期失败：在现有升级 PowerShell helper 的最后一次目标摘要校验后、提交前插入同步门，由独立进程改写隔离目标并放行 helper；helper 仍覆盖变化后的内容并报告已应用。这说明不遵守目标锁的并发写入存在校验与替换之间的窗口；实验使用插桩控制窄时序，不能据此认定遵守锁的常规更新必然发生。设计回滚时也必须处理该边界，不能直接照搬现有提交段。

`tests/test_update_atomic_copy_races.py` 曾复现三个竞争风险：暂存文件名被替换后失败清理可删除未知文件；提交前目标被替换可覆盖未知文件；POSIX 上暂存名被换成指向外部文件的符号链接后，`copystat` 可更改外部文件权限。前两项在 Windows 隔离目录复现，三项在 WSL 复现；均使用插桩控制竞争时序。当前已改为通过打开的暂存文件句柄设置元数据，失败时保留暂存路径，Windows DACL 也在核对文件身份后通过句柄设置；暂存清理和 POSIX 权限反例已转为通过。**提交前目标被替换仍可能被覆盖**，保留严格预期失败；暂存路径在最终检查与替换之间也仍可能被换。当前回滚复制备份模式，但未恢复原目标 POSIX owner/group；macOS 和真实异常恢复尚未验收。事务锁不能约束不遵守协议的外部写入。

更新记录、候选、备份、凭据、暂存和 DACL 操作现在拒绝缺失或为零的 inode 身份，以免两个无法区分的对象被误认为同一文件；设备号为零本身仍允许。特殊文件系统若无法提供非零 inode 会保守拒绝更新并保留证据，网络或特殊文件系统的兼容性未实测。

另一个隔离原型验证了可通过受保护的 Windows 文件句柄将目标无覆盖重命名到保留名；但目标会暂时缺失，还需要持久事务、崩溃恢复、重解析点和硬链接、ACL、文件系统差异与外部竞争等验证，尚不足以接入运行路径。

拟议的实现应作为一个完整协议验证，至少满足：

1. **健康启动租约**：对同一目标 EXE，在未确认阶段使用独立于更新锁、按目标路径绑定的跨进程独占租约。租约所有者在进入业务前完成健康决议；其他正常启动等待或明确失败，不能并发确认或继续业务。获得租约后必须重新读取目标、健康记录和事务；目标已确认且归属一致时才可释放。健康计数或回滚决议不能持久化时，本次启动不得进入业务或确认。每次启动按真实结果确定退出码和提示。
2. **生命周期与锁顺序**：现有 `ResourceLock` 的线程锁和重入身份绑定线程，不能由主线程取得后在后台线程释放；可评估专职线程持有、确认后由同一线程释放的设计，并验证后台线程启动失败、主进程退出、短命令、取消和崩溃。锁顺序拟为健康租约 → 更新数据锁 → 目标锁，等待进程退出的 helper 不持锁。`freeze_support()` 的 worker、普通命令、交互菜单和 `--post-update` 必须分别覆盖，不能让 worker 递归申请租约或让后者跳过必要的健康保护。
3. **Windows 延迟恢复**：回滚必须有独立任务与启动意图，保留原升级任务索引、健康记录和备份；不能直接复用会建立升级任务并重写健康记录的 `update_windows.schedule()`。等待的必须是原宿主的可靠进程身份，不能只凭 PID 判断；可研究受限且明确继承的原进程句柄，需以真实 Windows 验证。不得把执行核对的临时 worker 当成宿主，也不得终止未知进程。启动已调度、恢复已提交、恢复失败和身份不明是不同状态；未知 helper 存活状态不能盲目重复调度。
4. **提交与恢复**：helper 等原宿主退出后，按约定顺序取更新和目标锁，重新验证 health、原升级 job、backup receipt、完整 prepared 事务、目标及备份身份与 SHA。仅在目标目录创建归属明确的随机临时文件，校验内容、保留目标权限并原子替换；其他仍在运行的实例阻止替换时保持失败和全部证据。替换已提交后即使写回执失败，也必须根据目标实际摘要完成事务恢复，不得误报为未替换；只有证明原升级任务可以退休后才更新索引。恢复失败和记录不明时不得删除备份、health 或未知数据。
5. **确认边界**：健康确认必须持有正确租约，重读并验证当前可执行文件摘要、目标事务和 health 的 build、backup、job 归属；已请求或已准备回滚的版本不得确认。仅在本进程设置禁止标志不够：健康记录写入失败后，另一个已运行进程仍可读取旧记录并确认。多个数据目录共用目标时必须统一目标租约并在目标锁下复核，不能只按数据目录互斥。

待设计决定包括：租约争用的等待上限和用户提示、调度后退出码、是否提供安全的手动重试，以及重启后是否重放原命令。自动重放可能重复执行安装或卸载，未明确幂等性前不能默认重放。旧版进程不会遵守新增租约，跨版本混跑不能声称受该协议保护；需要决定迁移期间如何检测或保守拒绝，无法可靠识别时保留证据并提示处理。

验收必须覆盖同一与不同数据目录的真实多进程竞争、锁获取/线程启动/计数写入/事务写入失败、进程崩溃释放、helper 意图与 ACK 丢失、PID 复用、目标或备份被换、第二个进程仍占用 EXE、替换前后中断与重复恢复、老版本混跑、短命令和 `--post-update`。最后使用新构建的隔离真实 Windows 冻结包执行签名测试更新、连续短启动触发回滚、核对 v7/v8 摘要与原备份和任务退休，并分别记录尚未验收的平台和正式签名。上述方案和清单均待实现及验证。

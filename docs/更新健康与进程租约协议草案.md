# 更新健康与进程租约协议草案

> **设计草案，尚未接入生产流程。** 本文描述待设计、实现和验证的协议，不表示现有版本已提供这些保证。现状和已验证风险以[启动至首屏审查与待办](启动至首屏审查与待办.md)为准。

## 目标与范围

一个可执行文件可能被多个进程、多个 `OPSKIT_DATA_DIR` 同时使用。更新健康判断必须对应真实的更新事务和原数据目录；健康记录写入失败后不能继续执行业务，其他进程也不能把该失败当成成功确认。恢复必须保留原始可执行文件、备份和事务证据。

普通命令的成功、取消和业务错误都不等同于程序崩溃。短命令不应因为运行时间短而触发自动回滚。帮助和版本等不进入业务的路径可独立处理，但仍需考虑 Windows 加载中的可执行文件对替换的影响。旧版本和不遵守协议的进程无法被新协议锁约束。

## 事务归属

目标旁的事务记录需要版本化，记录目标的规范化路径、转换前后 build 和摘要、事务 ID、更新所属数据目录及其原生目录身份、备份 ID 和原更新 job ID。Windows 调度在准备事务前预分配 job ID；Unix 没有 job 时须明确表示不存在，而不是制造一个没有对应记录的 ID。备份凭据、job、目标事务及健康记录必须在对应锁下相互核对。

目录身份需要由实际打开的目录句柄获得，拒绝符号链接、junction 和其他重解析点；Windows 设计应验证卷序列号和文件 ID，Unix 设计应验证设备和 inode。路径相同不证明目录身份相同。平台或文件系统无法提供可靠身份时应停止自动决策并保留证据，不能退化成仅比较路径。Windows 实际 API、权限和网络文件系统支持仍需测试确认。

回滚使用独立的回滚 job ID，不覆盖原更新 job 索引。事务序列化后交给异步 helper 的 prepared 记录必须与目标记录一致；当前 helper 比较完整 prepared 内容，因此不得在其执行前擅自更改该记录。恢复时还需检查目标摘要、备份身份和摘要、事务 ID、原更新 job 与健康记录之间的对应关系。

这些校验用于识别协议归属和意外变化，不证明能够抵御有权同时篡改所有记录的同一账户。

## 状态和原子性

建议把健康决策和启动 attempt 纳入目标级事务的单一原子持久记录，使以下变化不会因为跨文件写入中断而相互矛盾；具体 schema 和原子写入、持久化语义须由实现与故障注入测试最终确定：

| 状态 | 含义 | 允许的下一步 |
| --- | --- | --- |
| 更新已应用、待观察 | 目标字节与新版本一致，尚无正在观察的启动 | 在拥有合法租约时记录新的 attempt，然后进入业务 |
| attempt 活跃 | 记录唯一 nonce、事务 ID、进程身份及阶段 | 正常退出关闭 attempt；达到已定义的健康条件则原子确认；异常终止留待下一次判定 |
| attempt 已正常关闭 | 一次启动正常结束，但短命令可能未达到健康观察条件 | 后续启动可建立新的 attempt，不增加失败次数 |
| 待回滚 | 未关闭 attempt 经核验后累计达到阈值，回滚决定已持久化 | 校验归属和备份，调度或执行恢复；不能再确认该版本健康 |
| 已确认 | 健康观察条件满足且确认已持久化 | 允许后续正常启动；按独立回收协议清理证据 |

启动时先在锁下读取并校验事务、目标字节和归属。当前数据目录与未确认事务的 owner 不匹配时，不能在当前目录另建健康记录，也不能推测或修改其他目录；应中止需要该决策的业务并给出可操作的恢复提示。已确认状态也必须来自可验证的目标级权威记录，不能仅凭当前目录没有 health 文件推断。

attempt 必须在进入业务前持久化成功。下次获得决策权时，仅将属于同一事务且仍未正常关闭的旧 attempt 作为异常终止证据；持久化失败时不进入业务，保留记录并报告错误。attempt 关闭、失败计数和健康确认不得分成可能相互矛盾的独立提交。机器断电或被外部强制终止也会留下未关闭 attempt，因此该证据只说明没有正常关闭，并不能证明原因是程序缺陷。

健康确认必须由当前 attempt 的合法持有者、在重新验证目标事务和字节后完成。交互界面达到就绪条件并持续观察后可确认；短命令正常退出只关闭 attempt，不凭运行很短就确认健康或计为失败。业务非零退出、用户取消、解析错误和进程异常需要按入口阶段明确分类，不能只依赖退出码或无结果信息的 `call_on_close`。`--post-update` 和不会调用 `_boot` 的 JSON 等命令必须纳入同一入口契约。

## 进程生命周期与锁顺序

单个健康决策排他租约只能防止并发健康确认，不能证明没有其他旧版本进程仍在执行。若允许多个正常实例，需要可跨进程验证的目标级共享生命周期锁：业务进程在其整个相关生命周期内持共享锁，替换和回滚持排他锁，并在替换前确认所有受保护实例已经退出。升级发起者必须先交接并释放自身锁，不能持共享锁等待自己获得排他锁；异步 helper 等待原宿主退出时不得持有会阻塞宿主退出的锁。

当前 `ResourceLock` 为排他锁且按线程持有，不提供上述共享锁或升级语义。它不能被直接视为已实现此方案。若改用全生命周期排他锁，会将正常使用变成目标级单实例，必须明确评估兼容性并验证后才能采用。多进程 worker、异常退出、进程句柄复用、进程存活未知，以及锁的继承和释放均需专门设计。无法确认 helper 或相关进程已退出时，不得重复调度或重放原命令。

健康决策、更新数据和目标锁的统一顺序、helper 的交接点、获取失败后的退出行为，须在接入前明确并通过跨进程测试证明无死锁。现有更新/恢复锁顺序为更新数据资源后目标资源；新增生命周期锁与之如何组合尚待设计，不能让后台确认线程与退出线程相互等待。

## 旧事务与恢复

现有目标事务不含数据目录归属或目标级健康确认状态，不能仅因目标事务已 applied 就认为健康确认完成。旧事务只可在完整且唯一的关联证据足以证明 owner 时设计迁移；证据不足、冲突、记录损坏或进程状态未知时，应拒绝自动恢复，保留目标、备份、job、health 和日志供诊断。不得按当前 `OPSKIT_DATA_DIR` 猜测归属或重置失败计数。旧版还可能不持新锁，因此跨版本并发保证必须单独说明。

## 接入前必须验证

使用临时目标和隔离数据目录，禁止对真实用户安装或数据注入故障。除单元测试外，至少需要实际多进程验证：

1. 同一目标、相同与不同数据目录并发启动；任何时刻只有合法持有者能够修改该事务的健康决策，错目录无法确认或恢复。
2. 写入 attempt、计数、关闭及确认的每个持久化边界注入失败或终止，重启后不会跳过判定、凭空确认、重复计数或丢失备份。
3. 正常短命令、非零业务结果、用户取消、异常终止和长时间交互分别验证；`--post-update`、JSON、子命令、帮助和版本入口各自覆盖。
4. 更新和回滚与多个长存活实例、后台 worker、退出阶段及 helper 竞争；确认锁顺序不会死锁，任何未获排他权的替换都不会执行。
5. 新旧记录迁移、缺失或替换目录、链接、损坏记录、不匹配摘要、helper 存活未知、重启和重复恢复均保持 fail-closed；检查无越权数据写入。
6. 在 Windows 和 Unix 真实文件系统分别验证锁、目录身份、原子替换及 crash 持久性；网络文件系统和异常权限另行记录。未测平台不能宣称通过。

完成条件是入口、状态存储、生命周期锁、更新 helper、回滚 helper 和迁移方案全部接入，并通过上述测试与隔离环境端到端验收；单独的锁原语或模拟测试不构成完成。
